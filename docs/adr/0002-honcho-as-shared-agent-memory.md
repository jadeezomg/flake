# 0002 — Honcho as the shared cross-agent memory system

**Status:** accepted

We adopt **Honcho** (`plastic-labs/honcho`, AGPL-3.0, self-hosted) as the single memory layer shared by every coding agent on every host — Claude Code, hermes, and omp — backed by one Honcho instance on `mini` and reached over Tailscale. The goal is one evolving model of the user that all agents read from and write to, rather than per-agent silos. Honcho won over the 2026 field (Mem0, Letta, Zep/Graphiti, Cognee, Memori, txtai, agentmemory, and later Signet AI) on three criteria: (1) it is purpose-built for *multi-participant shared state* — its Workspaces → Peers → Sessions model treats each agent (or human) as a peer in a shared workspace, which maps directly onto "all agents share one memory"; (2) its distinctive value is **theory-of-mind dialectic reasoning** — an evolving per-peer representation synthesized by a background deriver, not just vector recall, which is the capability we actually build the integrations around; (3) it ships a first-class Claude Code plugin plus MCP + REST, and is mature (server v3.0.9, large community) versus the alternatives. It was also already deployed on `mini` (Phase 1, see `docs/handoffs/02-honcho-llm-finalize.md`), so adoption cost was low.

## Coupled decisions

**One shared workspace, per-agent peers.** All agents use a single workspace `jadee` with one user peer `jadee`; each agent is a distinct AI peer (`claude`, `hermes`, `omp`). This is what makes memory shared — the user's evolving representation is common, while each agent keeps its own observations. ⚠️ The per-tool defaults actively work against this: the `claude-honcho` plugin defaults the workspace to `claude_code`/`cursor`/`obsidian`, which would silently split memory. The shared workspace **must be pinned** on every client.

**Self-hosted, no-auth, tailnet-gated.** Honcho runs with `USE_AUTH=false` behind the host firewall (only `tailscale0` trusted). The API binds loopback `127.0.0.1:8100`; `tailscale serve` fronts HTTPS at `https://mini.quokka-qilin.ts.net:8100`. SDK clients accept a dummy bearer (`sk-no-auth`); local/loopback `baseUrl`s auto-skip auth entirely. On-`mini` clients (hermes) talk loopback directly; off-host clients use the Tailscale name. The server is **v3-only** (API 3.0.9; `/v1`/`/v2` → 404). SDK base URLs are passed as the **bare origin** — `@honcho-ai/sdk` prepends `/v3` itself.

**Each agent integrates differently — there is no one mechanism.** Claude Code uses the official `claude-honcho` plugin (Claude's `SessionStart`/`UserPromptSubmit` hooks for auto-injection + an MCP server for tools), configured via `env` in `data/agents/global/settings.json`; it requires `bun` (the `web` devenv profile). hermes uses its **native** Honcho memory provider (`settings.memory.provider = "honcho"`, `extraDependencyGroups = ["honcho"]`, identity carried in a `honcho.json` installed to `$HERMES_HOME` via an activation snippet, since the module's `documents` option targets `workingDirectory` instead). omp has **no native pi/omp integration upstream**, so we ship a dependency-free hook (`data/agents/omp/hooks/honcho-context.ts`, live-symlinked into `~/.omp/agent/hooks/`) that hits the `/v3` dialectic endpoint with bun's `fetch` and injects a `<memory-context>` message on `before_agent_start`, fail-open. (omp is the pi family from ADR-0001; honcho config rides the same `~/.omp/agent` convention.)

**Deriver runs on the local LLM tier.** Honcho's deriver and dialectic `chat()` calls route to `mini`'s local chat server (`DERIVER_MODEL_CONFIG__OVERRIDES__BASE_URL = host.containers.internal:<miniLlmPort>`, served name `host.miniLlmServedName` — abstracted across vLLM/llamacpp). This keeps reasoning token-cost-free but competes with interactive chat for the GPU; the per-prompt dialectic call is the main contention point, tunable per client (`skipDialectic`, cadence knobs).

**The open-core concern is rejected as a reason to switch.** Honcho's entire engine — deriver, dialectic, dreamer, embeddings, vector store, chat/conclusions endpoints — is in the AGPL OSS repo and runs fully self-hosted. `app.honcho.dev` is the managed-cloud signup/billing portal, **not** a self-hostable dashboard withheld from the OSS product; no closed dashboard repo exists. We drive everything via API + MCP and use no dashboard. AGPL's network-copyleft creates no obligation for a private personal/tailnet deployment.

## Out of scope / future work

1. **omp MCP tools.** omp currently gets auto-injection (the hook) but no model-invoked tools. The official `@honcho-ai/mcp` is incompatible — its SDK (`@honcho-ai/core@2.2.0`) targets `/v2`, our server is v3-only. The only v3-compatible path is packaging `claude-honcho`'s `mcp-server.ts` (a bun app on the v3 `@honcho-ai/sdk`) as a Nix package exposing `search`/`chat`/`create_conclusion`. ⚠️ The shared MCP registry `lib/mcp-servers.nix` (`availableSharedServers`) fans out to Claude too (`claude-mcp.nix`), where it would collide with the plugin's own `honcho` MCP server — any honcho entry must be scoped to pi/omp only, not the shared set.

2. **omp write-back.** The omp hook is read-only: it consumes shared memory but does not persist omp's turns to Honcho (no session resolution + `add_messages`), so omp doesn't contribute to the shared representation. Bidirectional sync is a follow-up.

3. **Embeddings off.** `EMBED_MESSAGES=false` (clean first boot — semantic search disabled). Re-enable against a local embedding endpoint (mini's vLLM jina instance, currently disabled), minding vector dimensions. Until then, recall is text/derivation-only. Tracked in `docs/handoffs/02-honcho-llm-finalize.md`.

4. **Per-feature LLM endpoints.** Only `DERIVER_MODEL_CONFIG__*` points at the local server; other features (dialectic, summary, …) fall back to `api.openai.com` with a placeholder key. Wire `<FEATURE>_MODEL_CONFIG__*` per feature. Also in the handoff doc.

5. **Signet AI as a watch item, not a migration.** `Signet-AI/signetai` is genuinely better-aligned on several axes that matter for `mini`: far lighter (one Bun daemon + SQLite + local ONNX embeddings — no Postgres/Redis/deriver), Apache-2.0, a free self-hosted dashboard, `team`/`hybrid` network auth that fits tailnet sharing, and **native connectors for Claude Code, Pi, Oh My Pi, and Hermes** (which would replace our hand-rolled omp hook and the blocked omp MCP). But it is too young to bet shared infrastructure on (≈4 months old, ~196★, every release a prerelease, churns multiple times per day, opaque backing org), and it solves a *different* problem — custody/provenance/repairable-memory + portability, **not** theory-of-mind reasoning, which is what we built around. Revisit when Signet tags a stable (≥1.0) release. The condition that would flip this decision: if our priority shifts from *evolving user modeling* to *minimal ops + a UI + harness portability*. Evaluation path is a **parallel spike** (single container on `mini` alongside Honcho, point one agent at it, compare recall quality), never an in-place teardown.

6. **hermes Phase-2 model config.** hermes' memory is wired but the service still needs its model/provider config (e.g. OpenRouter via sops `hermes/env`) to actually run; `extraDependencyGroups = ["honcho"]` triggers a uv venv rebuild on the next `mini` switch.

7. **`mini` credential pipeline.** Honcho is currently no-auth/tailnet-gated, sidestepping the headless-host keyring gap noted in ADR-0001 item 5. If Honcho auth is ever enabled, the API key needs a sops-decrypted-at-runtime path on `mini` (no libsecret daemon there).
