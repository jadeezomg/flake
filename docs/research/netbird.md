# Research: NetBird as homelab network infrastructure

**Status:** research notes (2026-08-08)
**Scope:** primary sources only — `netbirdio/*` repository source and READMEs, `docs.netbird.io` (source: `netbirdio/docs`), `LICENSE` files, `netbird.io/pricing`, nixpkgs source, GitHub Security Advisories, OSV.
**Verdict:** NetBird is a true peer mesh VPN, like Tailscale, plus a public reverse proxy that Tailscale does not have. NixOS packaging is excellent for the client and stale for the server. The declarative story is an official Terraform provider, not a policy file.

---

## 1. What NetBird is

NetBird builds a WireGuard overlay network between your machines. A central Management service holds the network state. The agents form direct encrypted tunnels to each other. The README states it directly: "NetBird combines a configuration-free peer-to-peer private network and a centralized access control system in a single platform, making it easy to create secure private networks for your organization or home" ([README](https://github.com/netbirdio/netbird/blob/main/README.md)).

**Publisher.** NetBird GmbH, Berlin, Germany. The `LICENSE` file carries "Copyright (c) 2022 NetBird GmbH & AUTHORS". Security reports go to `security@netbird.io` ([SECURITY.md](https://github.com/netbirdio/netbird/blob/main/SECURITY.md)).

**Funding.** The company took a pre-seed round in 2023 and a Series A in 2026. NetBird came out of the CISPA Incubator ([cispa.de](https://cispa.de/en/netbird-series-a)). The README records a grant from the German Federal Ministry of Education and Research through the StartUpSecure program.

**Commercial model.** Two delivery paths:

1. **NetBird Cloud** — managed SaaS at `app.netbird.io`. Priced per active user.
2. **Self-hosted** — free Community Edition, or a paid Enterprise Commercial License. See § 8.

## 2. Architecture

### 2.1 Component roles

The docs name four components ([how-netbird-works](https://docs.netbird.io/about-netbird/how-netbird-works)): "NetBird relies on four components - **Client** application (or agent), **Management**, **Signal** and **Relay** services."

| Component | Plane | Role |
|---|---|---|
| **Client** (`netbird` agent) | Data | Generates the WireGuard keys, runs ICE, manages the `wt0` interface. "The private key, generated by the NetBird client, never leaves the machine." |
| **Management** | Control | "It keeps the network state, public WireGuard keys of the peers, authenticates and distributes network changes to peers." Also assigns IPs from `100.64.0.0/10`. |
| **Signal** | Control | Carries ICE candidates between peers. "It does not store any data and no traffic passes through it." Messages are point-to-point encrypted. |
| **Relay** | Data (fallback) | Forwards encrypted WireGuard packets when hole punching fails. |
| **Dashboard** | Control | Admin web UI. Separate repo, [netbirdio/dashboard](https://github.com/netbirdio/dashboard). |

Since v0.62 a single `netbird-server` container holds Management, Signal, Relay, and STUN. The docs describe it as a "Combined server that includes management, signal, relay, and embedded STUN in a single container. Configured via config.yaml" ([configuration-files](https://docs.netbird.io/selfhosted/maintenance/configuration-files)).

### 2.2 Mesh, not hub-and-spoke

This is the core difference from Pangolin. The docs are explicit: "With NetBird clients installed and authorized on the Management service, **machines form a mesh network connecting to each other directly via an encrypted point-to-point WireGuard tunnel**" ([how-netbird-works](https://docs.netbird.io/about-netbird/how-netbird-works)).

Access policies prune the mesh. "While it is possible to create a full mesh network, it might be not a desirable outcome. In this case, groups and access controls can be utilized to limit the access to certain machines."

Since v0.50.1 a "lazy connection" mode opens tunnels only on demand, with a 15-minute idle teardown ([lazy-connection](https://docs.netbird.io/manage/peers/lazy-connection)).

### 2.3 NAT traversal

NetBird uses ICE through the `pion/ice` library. "NetBird uses the **ICE (Interactive Connectivity Establishment)** protocol to find the best possible connection path between two peers. ICE is the same technology that powers WebRTC video calls" ([understanding-nat-and-connectivity](https://docs.netbird.io/about-netbird/understanding-nat-and-connectivity)).

The same page gives the candidate priority order:

```
Priority 1: Host ↔ Host                        (direct LAN connection)
Priority 2: Host ↔ Server Reflexive            (direct through NAT)
Priority 3: Server Reflexive ↔ Server Reflexive (both behind NAT)
Priority 4: Relay ↔ Any                        (fallback via relay server)
```

The client needs no inbound firewall port. "The NetBird client **does not require any inbound ports** on your network firewall — peers initiate all connections outbound and use ICE/STUN for NAT traversal" ([ports-and-firewalls](https://docs.netbird.io/about-netbird/ports-and-firewalls)).

### 2.4 Relay versus direct

Coturn was the old relay. NetBird replaced it: "starting with v0.29.0, a new WebSocket-based relay has been introduced with the intent of replacing the previous TURN relay (Coturn)" ([how-netbird-works](https://docs.netbird.io/about-netbird/how-netbird-works)). The current relay races QUIC and WebSocket and takes whichever connects first.

Relayed traffic stays encrypted. "Similar to Signal, traffic that flows through the Relay cannot be decrypted due to the WireGuard point-to-point encryption."

### 2.5 How to tell direct from relayed

Run `netbird status --detail`. Per-peer fields ([troubleshooting-client](https://docs.netbird.io/how-to/troubleshooting-client)):

```
Connection type: P2P
Direct: true
ICE candidate (Local/Remote): host/host
ICE candidate endpoints (Local/Remote): 10.128.0.35:51820/10.128.0.54:51820
Latency: 3.2ms
```

`Connection type` reads `P2P` or `Relayed`. The candidate pair tells you which side failed. The docs give the decoder: `host` is a local interface address, `srflx` is a STUN-discovered public address, `relay` means hole punching failed on that side.

## 3. Performance and speed

### 3.1 Kernel WireGuard on Linux

NetBird uses the kernel WireGuard module on Linux. The README lists "Kernel WireGuard" as a feature. The source confirms it. `client/iface/iface_new_linux.go` prefers the kernel path:

```go
if device.WireGuardModuleIsLoaded() {
    return &WGIface{
        tun:            device.NewKernelDevice(...),
        wgProxyFactory: wgproxy.NewKernelFactory(opts.WGPort, opts.MTU),
    }, nil
}
```

`client/iface/iface_new.go` covers macOS, Windows, and FreeBSD. It has no kernel branch. Those platforms always set `userspaceBind: true` and use `wireguard-go`.

The docs say the same: "The capacity table above is **kernel WireGuard, the default on Linux when the `wireguard` kernel module is present**." And: "**The routing peer is not Linux.** Windows, macOS, and the other platforms forward in userspace regardless" ([sizing-routing-peers](https://docs.netbird.io/manage/networks/sizing-routing-peers)).

`netbird status -d` reports `Interface type: Kernel`.

**This is the main technical advantage over Tailscale.** Tailscale uses userspace WireGuard on every platform. On `desktop`, `framework`, and `mini` NetBird will use the kernel module. On `caya` (macOS) it will not.

### 3.2 First-party throughput numbers

From [sizing-routing-peers](https://docs.netbird.io/manage/networks/sizing-routing-peers). Test bed: AWS `c6in.16xlarge`, Xeon 8375C, 1280-byte tunnel MTU, direct connections.

| vCPUs | Kernel down | Kernel up | Userspace down | Userspace up |
|---|---|---|---|---|
| 1 | ~2 Gbps | ~2 Gbps | ~1.6 Gbps | ~1.4 Gbps |
| 4 | ~7 Gbps | ~4 Gbps | ~6.8 Gbps | ~3.5 Gbps |
| 16 | ~20 Gbps | ~15 Gbps | ~6.8 Gbps | ~3.7 Gbps |
| 64 | ~31 Gbps | ~15 Gbps | ~5.8 Gbps | ~4.4 Gbps |

Three quotes matter for media streaming:

- "**Userspace WireGuard does not scale across cores.** Download plateaus around 6.8 Gbps by four cores and climbs no further."
- "**One tunnel is about one CPU core.** A single client's tunnel is handled largely on one core, so it tops out at a few Gbps."
- Traffic of many small packets "runs materially lower, roughly half the download figure".

A 4K Jellyfin stream needs less than 150 Mbps. Every number above clears that by a wide margin, on both the kernel path and the userspace path.

### 3.3 Versus Tailscale

NetBird published a benchmark against Tailscale 1.96.4 and Cloudflare Mesh, on Ubuntu 24.04 with iperf3 ([knowledge-hub](https://netbird.io/knowledge-hub/cloudflare-mesh-vs-netbird-vs-tailscale)). It ran NetBird in userspace mode for a fair comparison: "To keep our comparison apples-to-apples, we ran NetBird in userspace mode for these tests."

Result: "**NetBird and Tailscale perform nearly identically across all tests.**" Both reached about 1,260 Mbps between two Hetzner sites. Cloudflare Mesh reached 250 Mbps.

Read this honestly. On equal footing NetBird and Tailscale tie. NetBird wins only because it can switch to the kernel module on Linux, which the vendor deliberately turned off for this test.

### 3.4 LAN peers connect directly — confirmed

**Yes. Two NetBird peers on the same LAN form a direct WireGuard tunnel over the local network.** This is the single most important finding for media streaming.

The docs define host candidates: "**Host candidates**: Local IP addresses on the machine (e.g., `192.168.1.50:51820`). These are gathered by **enumerating all network interfaces on the device**" ([understanding-nat-and-connectivity](https://docs.netbird.io/about-netbird/understanding-nat-and-connectivity)).

Host-to-host is ICE priority 1, above every NAT path and far above the relay. The source keeps host first in the candidate list (`client/internal/peer/ice/agent.go`):

```go
func CandidateTypes() []ice.CandidateType {
	if hasICEForceRelayConn() { return []ice.CandidateType{ice.CandidateTypeRelay} }
	return []ice.CandidateType{ice.CandidateTypeHost, ice.CandidateTypeServerReflexive, ice.CandidateTypeRelay}
}
```

The docs' own sample status output shows two peers on `10.128.0.0/24` talking over their LAN addresses with `host/host`.

**CAUTION: a host firewall can silently force LAN peers onto the relay.** The docs record this failure mode ([ports-and-firewalls](https://docs.netbird.io/about-netbird/ports-and-firewalls)):

> "**Symptoms**: P2P works when one peer is behind NAT but fails when both peers are on the same flat network; `netbird status -d` shows connection type as 'Relayed' instead of 'P2P' for local peers."

The cause is the absence of NAT state on a flat LAN. The fix is an inbound UDP allow rule on ports 49152-65535 for the `netbird` binary. On NixOS, set `services.netbird.clients.<name>.openFirewall = true`.

**Verify with `netbird status -d` after any change.** Look for `Connection type: P2P` and `host/host`.

### 3.5 Relay fallback cost

The NetBird relay is the DERP equivalent. "NetBird includes a **custom-built relay system optimized specifically for its use case** … Unlike traditional TURN servers, NetBird's relay uses a custom protocol designed for efficiency."

The cost is stated plainly ([troubleshooting-relayed-connections](https://docs.netbird.io/help/troubleshooting-relayed-connections)): "A relayed connection works. It just **adds latency and shares the relay's bandwidth** … **Relay server capacity is shared among users.** The trade-off is latency and throughput, never confidentiality."

No first-party statement caps relay bandwidth on NetBird Cloud. `netbird.io/pricing` bills per active user and per machine only. There is no bandwidth line item and no fair-use clause. Tailscale documents no DERP cap either. Treat both as undocumented rather than unlimited.

Self-hosted deployments carry their own relay: "When using the self-hosted version, you need to set up your own relay servers."

### 3.6 Quantum resistance

NetBird embeds Rosenpass. "Starting v0.25.4, the NetBird agent runs an embedded Rosenpass server that automatically rotates and applies WireGuard pre-shared keys to every point-to-point connection" ([post-quantum-cryptography](https://docs.netbird.io/client/post-quantum-cryptography)). It rotates the pre-shared key every two minutes.

Enable it with `netbird up --enable-rosenpass`. Three limits apply:

- "This is still an **experimental feature**, may contain bugs, and is **not supported on mobile devices**."
- "If the Rosenpass feature is enabled on a peer it will only be able to communicate with other peers that have Rosenpass enabled." Use `--rosenpass-permissive` to relax this.
- The reverse proxy does not support Rosenpass.

Rosenpass costs no throughput. It only supplies the WireGuard pre-shared key. It never sits in the packet path.

Tailscale has no equivalent shipped feature.

## 4. NixOS and declarative configuration

### 4.1 Packages

nixpkgs packages the client **and every server component**. All of them build from one derivation with a `componentName` override.

| Attribute | nixpkgs 25.11 (stable) | nixpkgs unstable (index) | nixpkgs master | Upstream latest |
|---|---|---|---|---|
| `netbird` (client) | **0.60.2** | 0.67.3 | **0.76.2** | 0.76.3 |
| `netbird-ui` | same | same | same | — |
| `netbird-management` | same | same | same | — |
| `netbird-signal` | same | same | same | — |
| `netbird-relay` | same | same | same | — |
| `netbird-proxy` | same | same | same | — |
| `netbird-upload` | same | same | same | — |
| `netbird-dashboard` | — | — | 2.90.9 | — |

The search index lags the tree, as it does for Pangolin. `pkgs/by-name/ne/netbird/package.nix` on master declares `version = "0.76.2"` while the unstable index still reports 0.67.3. Trust the source.

**There is no `netbird-combined` or `netbird-server` package.** The single-container server that upstream now ships by default is not packaged.

### 4.2 NixOS module

The module is large and well made. Files:

```
nixos/modules/services/networking/netbird.nix        # client
nixos/modules/services/networking/netbird.md
nixos/modules/services/networking/netbird/server.nix
nixos/modules/services/networking/netbird/management.nix
nixos/modules/services/networking/netbird/signal.nix
nixos/modules/services/networking/netbird/dashboard.nix
nixos/modules/services/networking/netbird/coturn.nix
nixos/tests/netbird.nix
```

**Client side — `services.netbird.clients.<name>`.** This is the strongest part. It supports many parallel clients, each with its own interface, port, state directory, and system group. Options include:

- `interface`, `port`, `openFirewall`, `openInternalFirewall`, `autoStart`, `logLevel`
- `hardened` — a dedicated user, a restricted daemon socket, minimal capabilities
- `login.setupKeyFile` — a path to a setup key, for unattended join
- `login.systemdDependencies` — order the join after a secret is decrypted
- `config` — arbitrary JSON merged into `config.json`
- `environment` — environment variables for the unit
- `dns-resolver.address` and `dns-resolver.port`
- `ui.enable` — a `netbird-ui` wrapper per client
- `services.netbird.useRoutingFeatures` — `none`, `client`, `server`, or `both`. It sets `rp_filter` to loose and enables IP forwarding.

`services.netbird.enable` remains as a compatibility alias for a single `default` client on port 51820, interface `wt0`.

`login.setupKeyFile` composes with sops-nix directly. Point it at the decrypted path and add the sops unit to `login.systemdDependencies`.

**Server side — `services.netbird.server`.** This works, but it tracks the **legacy pre-0.62 architecture**. Options: `domain`, `enableNginx`, `management.*`, `signal.*`, `dashboard.*`, `coturn.*`.

`services.netbird.server.management.settings` accepts the full `management.json` as a JSON value, with a `_secret` escape hatch that reads a value from a file at start. That is a real declarative win for sops-nix.

**Three gaps in the server module:**

1. **It requires an external IdP.** `oidcConfigEndpoint` has type `str` and no default, so it is mandatory. The module docs say so: "we need both a Coturn server and an identity provider" ([server.md](https://github.com/NixOS/nixpkgs/blob/master/nixos/modules/services/networking/netbird/server.md)). Upstream removed this requirement in v0.62 with an embedded Dex. The module has not caught up.
2. **It uses Coturn, not the new relay.** There is no `services.netbird.server.relay` option, even though `netbird-relay` is packaged. Upstream published a Coturn-to-STUN migration guide.
3. **There is no reverse-proxy option.** `netbird-proxy` is packaged, but no module drives it.

**There is no home-manager module.** `netbird` is a system daemon, so this is expected.

### 4.3 How declarative is the configuration, really?

Split the answer in two.

**Client side: fully declarative.** Package, interface, port, firewall, routing flags, and the setup key all live in Nix. A peer joins with no manual step.

**Control plane: object graph in a database, driven by an official Terraform provider.** There is no single policy file. Compare honestly to Tailscale:

| | **Tailscale** | **NetBird** |
|---|---|---|
| Policy format | One HuJSON document (`tailscale.com` policy file) | Discrete API objects |
| Edit as code | Yes, natively. Git-diffable | Yes, through Terraform or the REST API |
| Official IaC provider | `tailscale/tailscale` | `netbirdio/terraform-provider-netbird` (BSD-3) |
| Kubernetes CRDs | Yes | Yes — `netbirdio/kubernetes-operator` |
| Whole-config export | The policy file *is* the config | No documented dump or restore |
| Reviewable diff | A single file diff | A Terraform plan |

**Tailscale wins on reviewability. NetBird wins on coverage.** A Tailscale ACL file covers access rules, tags, node attributes, and SSH. It does not cover DNS records, routes, or device enrollment. The NetBird Terraform provider covers 24 resource types:

`netbird_account_settings`, `netbird_agent_network_guardrail`, `netbird_agent_network_policy`, `netbird_agent_network_provider`, `netbird_agent_network_settings`, `netbird_dns_record`, `netbird_dns_settings`, `netbird_dns_zone`, `netbird_group`, `netbird_identity_provider`, `netbird_nameserver_group`, `netbird_network`, `netbird_network_resource`, `netbird_network_router`, `netbird_peer`, `netbird_policy`, `netbird_posture_check`, `netbird_reverse_proxy_domain`, `netbird_reverse_proxy_service`, `netbird_route`, `netbird_scim`, `netbird_setup_key`, `netbird_token`, `netbird_user`.

**What Terraform cannot do:**

- **It cannot create a peer.** The docs say: "This resource doesn't create the Peer itself but manages it." A peer must enroll with a setup key first. Terraform then manages `name`, `ssh_enabled`, `approval_required`, and the expiration flags.
- No resource for audit events, billing, or IdP-synced groups.
- No resource for reverse-proxy clusters. That is a data source only.
- **No whole-account export or import.** Terraform state is the only record.

**There is no management CLI.** The `netbird` binary is the client agent. Its subcommands are `up`, `down`, `login`, `status`, `networks`, `ssh`, `expose`, `debug`, `profile`, `service`, and a few more. Only `expose` writes control-plane config, and only for the life of the process.

**Practical read for this flake.** You will run two config systems: Nix for the peers, and Terraform (or `terraform-nixos`-style wrapping, or a `just` recipe over the REST API) for the control plane. Today the Tailscale ACL file is one JSON document in the repo. NetBird replaces that with a Terraform module and a state file. That is a real increase in moving parts, but the result is still code, not dashboard clicks.

### 5.1 Reaching the Unraid NAS

Use a Network, not the deprecated Routes. The docs are clear: "**Routes are deprecated.** Every use case except exit nodes has moved to Networks."

Steps for a LAN-only device:

1. Create a Network.
2. Add a resource. Use a `/32` for one host. The docs advise it: "For Zero Trust least privilege, prefer single-host `/32` resources over broad ranges."
3. Assign a LAN-side peer as routing peer. `mini` is the natural choice.
4. Write an access policy from your user group to the resource group.

Masquerade is on by default: "the routing peer masquerades the traffic, rewriting the source to its own LAN IP, so the destination network needs no awareness of NetBird."

**One trap.** A network resource policy does not grant access to services on the routing peer itself. The docs split the two paths: "THROUGH the routing peer → forward chain → network resource policy" against "TO the routing peer → input chain → peer-to-peer policy". You need both policies if `mini` serves the routes and also runs Jellyfin.

### 5.2 Access policies

The model is deny by default with allow-only rules. "Without policies, a network operates by denying traffic, meaning peers cannot communicate with each other." And: "Because you can only create ALLOW policies, there is no processing order or priority."

Policies carry a protocol (`ALL`, `TCP`, `UDP`, `ICMP`, `netbird-ssh`), ports, port ranges since v0.48, a direction flag, and optional posture checks.

Groups replace tags: "A NetBird group works and follows a similar concept to tags in other platforms."

## 6. Public ingress

**Yes. NetBird has a Funnel equivalent, and it is self-hostable.** This is the biggest surprise in this research.

From [reverse-proxy](https://docs.netbird.io/manage/reverse-proxy):

> "NetBird Reverse Proxy lets you expose internal services running on peers or behind network resources to the public internet. NetBird handles TLS termination, optional authentication and access restrictions, and proxies incoming traffic through the NetBird mesh to reach the target service, all without opening ports or configuring firewalls on your internal machines."

> "**Availability:** Reverse Proxy is currently in **beta**."

**It is genuinely public.** The docs warn about it: "Public services are accessible to anyone on the internet who knows the URL."

**Certificates.** "When you create a reverse proxy service, NetBird provisions a public domain with an automatic TLS certificate." Self-hosted installs get three modes:

| Mode | Detail |
|---|---|
| ACME | Let's Encrypt per domain. `NB_PROXY_ACME_CHALLENGE_TYPE`, default `tls-alpn-01` |
| Static | Your own certificate and key files |
| Wildcard | A directory of wildcard certificate and key pairs |

**Protocol modes.** HTTP is Layer 7 with TLS terminated at the edge. TCP, UDP, and TLS are Layer 4. TLS mode is passthrough: "The proxy inspects the TLS ClientHello to read the SNI hostname and forwards the encrypted connection to your backend without terminating TLS."

**Authentication in front of a public service** ([reverse-proxy/authentication](https://docs.netbird.io/manage/reverse-proxy/authentication)): SSO/OIDC, shared password, numeric PIN, header auth (API key, Bearer, Basic), IP-CIDR restriction, country restriction, and CrowdSec IP reputation. This meets the zero-trust and 2FA goal.

**A private mode also exists**, the Tailscale Serve equivalent: "**NetBird-Only Access** turns the service into a private service … Use it when you want a service exposed only inside your NetBird mesh."

**A CLI exists** ([expose-from-cli](https://docs.netbird.io/manage/reverse-proxy/expose-from-cli)):

```
netbird expose 8080
netbird expose --with-password safe-pass 8080
netbird expose --protocol tcp --with-external-port 15432 5432
netbird expose --protocol tls --with-custom-domain tls.example.com 4443
```

Services created this way are ephemeral. They exist only while the command runs.

**Two self-hosted constraints:**

1. "Self-hosted deployments **must** use Traefik as their external reverse proxy. Traefik is the only supported reverse proxy that provides TLS passthrough."
2. Self-hosted needs a separate `netbirdio/netbird-proxy` instance that reaches Management over gRPC. The `getting-started.sh` script includes it from v0.65.0 when you pick built-in Traefik.

**Cost to the current design.** Constraint 1 conflicts with the Caddy plus `caddy-tailscale` setup. You keep Caddy for the 16 `*.jadee.fyi` vhosts, or you move public vhosts to the NetBird proxy with Traefik. NetBird Reverse Proxy is in beta, and `netbird-proxy` has no NixOS module. Keeping Caddy is the lower-risk path.

**Pairing with a reverse proxy.** The straight swap keeps today's shape. Run Caddy on a NetBird peer instead of a tailnet node. It reaches every backend over `wt0`, terminates TLS with Let's Encrypt through Cloudflare DNS-01, and keeps zero public ingress. NetBird replaces only the mesh layer. The `caddy-netbird` plugin exists as a community project, listed in the NetBird README, but it is not first-party.

## 7. Self-hosting

### 7.1 What you must run

The modern combined deployment is small. Three containers are mandatory.

| Service | Image | Mandatory |
|---|---|---|
| `netbird-server` | `netbirdio/netbird-server` | **Yes** — Management + Signal + Relay + STUN |
| `dashboard` | `netbirdio/dashboard` | **Yes** in practice — it is the admin UI |
| `traefik` | `traefik:v3.6` | A TLS-terminating proxy is required. Traefik is the default |
| `proxy` | `netbirdio/reverse-proxy` | No — only for public ingress |
| `crowdsec` | `crowdsecurity/crowdsec` | No |

Coturn is gone from new installs. The docs mark the old guide clearly: "This guide uses the **older multi-container architecture** with separate `management`, `signal`, `relay`, and `coturn` containers, configured via `management.json`" ([selfhosted-guide](https://docs.netbird.io/selfhosted/selfhosted-guide)).

### 7.2 No external IdP is required

This corrects the most common stale claim about NetBird.

From [identity-providers](https://docs.netbird.io/selfhosted/identity-providers):

> "By default, NetBird does not require an external identity provider. New installations include a built-in authentication system that lets you create and manage users directly through the Dashboard using local username and password authentication. **External identity providers are entirely optional.**"

The built-in IdP is an embedded Dex: "NetBird includes built-in local user management powered by an embedded [Dex](https://dexidp.io/) server" ([selfhosted-quickstart](https://docs.netbird.io/selfhosted/selfhosted-quickstart)). `combined/config.yaml.example` marks it "always enabled". Local TOTP MFA is built in and free.

The change landed in v0.62: "Previously, self-hosting required setting up and maintaining a separate identity provider (like Zitadel, Keycloak, or Auth0). Now, the Management service supports local user management directly … **No external IdP required** … Fewer containers to deploy and maintain (4-5 vs 7+ previously) … Lower resource requirements (~1GB RAM vs 2-4GB previously)" ([self-hosted-vs-cloud](https://docs.netbird.io/about-netbird/self-hosted-vs-cloud)).

**The nixpkgs module does not have this yet.** `oidcConfigEndpoint` is still mandatory there. See § 4.2.

### 7.3 Specs and ports

From [selfhosted-quickstart](https://docs.netbird.io/selfhosted/selfhosted-quickstart):

> "A Linux VM with at least **1CPU** and **2GB** of memory. The VM must be publicly accessible on **TCP ports 80 and 443**, and **UDP port 3478**. A **public domain** name that resolves to the VM's public IP address."

That is the whole port list. The relay rides HTTPS on 443 as `rels://<domain>:443`. Management gRPC and Signal gRPC multiplex on 443 too. **There is no inbound WireGuard port on the server.**

Bare IP addresses are not supported. Cloudflare proxying must be off — set the record to DNS only.

The legacy split architecture needed far more: TCP 80, 443, 33073, 10000, 33080, plus UDP 3478 and UDP 49152-65535 for Coturn.

### 7.4 Docker only, or binaries?

**Upstream ships no server binaries.** `gh api repos/netbirdio/netbird/releases/latest --jq '.assets[].name'` on v0.76.3 returns the client agent, the GUI client, an IdP migration helper, install scripts, and a WASM build. There is no `netbird-management`, `netbird-signal`, or `netbird-relay` asset.

**But the components build fine from source, and nixpkgs proves it.** `pkgs/by-name/ne/netbird/package.nix` builds each component through a `componentName` override with `subPackages = [ component.module ]`. nixpkgs ships `netbird-management`, `netbird-signal`, `netbird-relay`, `netbird-proxy`, `netbird-upload`, and `netbird-dashboard` at 0.76.2 on master. The NixOS module runs them as systemd units with no container.

The gap is the `combined/` package. That directory is a single Go main with one `--config` flag. Packaging it is low effort. Nobody has done it.

### 7.5 Where state lives

**Config files, hand-editable:**

| File | Contents |
|---|---|
| `config.yaml` | The whole server config. "Replaces the old management.json and relay.env files" |
| `dashboard.env` | Dashboard API endpoints and OIDC client settings |
| `docker-compose.yml` | Service definitions |

**Database state:** accounts, users, peers, groups, policies, routes, posture checks, tokens, IdP connectors, activity events.

Three separate stores, from `combined/config.yaml.example`:

```yaml
  store:
    engine: "sqlite"  # sqlite, postgres, or mysql
  # activityStore:
  #   engine: "sqlite"  # sqlite or postgres
  # authStore:
  #   engine: "sqlite3"  # sqlite3 or postgres
```

All three live under `dataDir: /var/lib/netbird`. SQLite is the default: "SQLite is the default storage engine for NetBird Management. It requires no external dependencies and works out of the box for new installations" ([sqlite-store](https://docs.netbird.io/selfhosted/maintenance/sqlite-store)).

**CAUTION: back up `config.yaml` with the data directory.** `config.yaml` holds `encryptionKey` and `sessionCookieEncryptionKey`. If you lose the file, you cannot decrypt the store.

### 7.6 Operational burden — honest reading

Three containers, three config files, one volume, one DNS record. That is a small stack, and much smaller than the Zitadel-era setup that most old write-ups describe.

Upgrades are two commands, and schema migrations run at start:

```
docker compose pull netbird-server dashboard
docker compose up -d --force-recreate netbird-server dashboard
```

**Six real costs:**

1. **Every upgrade restarts the control plane.** The docs are candid: "**Direct peer-to-peer connections keep working throughout**, because they do not pass through your servers … recreating it restarts Relay and active relayed sessions reconnect. While the server is down you cannot change configuration, apply new policies, or onboard new peers."
2. **No HA without paying.** Active-active Management and Signal need the commercial license.
3. **You are the only relay.** "This a complex task and requires additional maintenance effort." Every NAT-hostile peer pair hairpins through your one VM.
4. **A public FQDN and a public IP are mandatory.** This is a real change from today. Tailscale's hosted control plane needs neither. Self-hosted NetBird needs a public box.
5. **Long-lived stream timeouts.** If you replace Traefik with your own proxy, you must disable read, write, and idle timeouts. gRPC and the relay WebSocket die otherwise. This is the classic self-hosted NetBird failure.
6. **Version skew between the server and the dashboard.** They version independently.

NetBird's own warning is worth quoting: "It is not an easy task to deploy and maintain such infrastructure in a reliable manner. NetBird is not just one VPN server."

**Compared to today.** The current setup has a hosted control plane and zero servers to patch. Self-hosted NetBird adds one public VM, one upgrade ritual, one backup job, and a single point of failure for policy changes. **NetBird Cloud plus NixOS clients keeps the current operational profile.** The self-hosted control plane is a separate decision, and it costs more than the flake gains.

### 8.2 How the commercial product is gated

**Not by a license key in the open source code.** Source searches return nothing:

- `licenseKey language:go` — zero results
- `IsEnterprise` — zero results
- `EnterpriseOnly`, `premium` — zero results

The OSS `netbird-server` build has no key check, no phone-home, no time limit, and no peer or user cap.

**Gating works by image substitution and no-op stubs.** `management/server/integrations/` holds interfaces only. The implementation comes from `github.com/netbirdio/management-integrations`. In the public GPLv3 repo that implementation does nothing. From `integrations/validator.go`:

```go
func (v *IntegratedValidatorImpl) IsNotValidPeer(...) (bool, bool, error) {
	return false, false, nil
}
```

Every peer validates as approved, always. The data model (`PeerApprovalEnabled`, `ApprovalRequired`) exists, and the API accepts it, but nothing enforces it. The commercial `netbird-server-cloud` image links the private implementation instead.

The commercial images (`ghcr.io/netbirdio/netbird-server-cloud`, `dashboard-cloud`, `flow-receiver-cloud`, `flow-enricher-cloud`) have no public repo. `getting-started-enterprise.sh` gates them behind an EULA: "NetBird's on-premise software is commercial software, licensed and not sold."

So the model is **open-core by image substitution**, not by crippled OSS code. That is cleaner than a paywalled monorepo, and it also means you cannot fork the paid features.

## 9. Risks

### 9.1 Maturity and momentum

Positive signals:

- 28,147 stars, 1,585 forks. Created 2021-04-14. Pushed the same day this note was written.
- 933 commits in the last 12 months, about 151 distinct contributors.
- Release cadence is very high: v0.68 through v0.76.3 in roughly four months, often several patch releases per week.
- Real funding, EU jurisdiction, an active hiring page.

Negative signals:

- **1,287 open issues against 1,554 closed.** 45 percent of every issue ever filed is still open. 268 open pull requests. Compare Pangolin at 73 open against 1,086 closed.
- **The bus factor is low.** Six contributors hold 2,645 commits. The seventh has 57. Development is one company team.
- **Still on 0.x.** Combined with latest-release-only support, the version number means no stability promise.

### 9.2 Security advisories

NetBird publishes GHSAs. That is better than Pangolin, which publishes none.

| ID | Date | Severity | Detail | Fixed |
|---|---|---|---|---|
| [GHSA-qcpp-8vwj-hhwr](https://github.com/netbirdio/netbird/security/advisories/GHSA-qcpp-8vwj-hhwr) | 2026-07-29 | High | Local privilege escalation through the unauthenticated daemon IPC socket | 0.76.0 |
| [GHSA-fhw6-5mff-2gfh](https://github.com/netbirdio/netbird/security/advisories/GHSA-fhw6-5mff-2gfh) | 2026-07-15 | High, CVSS 7.5 | Relay WebSocket goroutine leak. Resource exhaustion DoS | 0.68.0 |
| [GHSA-rxmp-8h9v-56cx](https://github.com/advisories/GHSA-rxmp-8h9v-56cx) | 2026-04-01 | Medium, CVSS 4.4 | Race in `UpdateUser`. Admin escalates to owner | 0.65.3 |

| [GHSA-9v35-4xcr-w9ph](https://github.com/advisories/GHSA-9v35-4xcr-w9ph) / CVE-2024-41260 | 2024-08-01 | High, CVSS 7.5 | Static initialization vector | 0.29.2 |

**The IPC advisory is the worst one for a homelab.** Every version from 0.5.0 (March 2022) to 0.75.1 exposed the client daemon gRPC control interface with no authentication. On Linux, macOS, and FreeBSD it was a world-writable Unix socket at `/var/run/netbird.sock` with mode 0666. Any unprivileged local user could read the VPN config, enable the embedded SSH server, enable SSH root login, disable SSH authentication, re-register the peer to an attacker's account, and then open a root shell. **That is a 3.5-year exposure window in a daemon that runs as root on every machine.** An outside researcher found it, not the vendor. PR #6967 fixed it with kernel-derived caller identity ([write-up](https://netbird.io/knowledge-hub/security-advisory-daemon-ipc-local-privilege-escalation)).

**Direct NixOS consequence:** nixpkgs **25.11 ships 0.60.2**, which is inside the affected range for both 2026 advisories. Do not deploy NetBird from stable nixpkgs. Use unstable, or pin the package through an overlay.

### 9.3 Disclosure policy and audits

[SECURITY.md](https://github.com/netbirdio/netbird/blob/main/SECURITY.md) was rewritten on 2026-07-31. It promises acknowledgment, a joint severity assessment, a written explanation for any downgrade, a published GHSA, and reporter credit. Two gaps: **no PGP key** and **no named response time**.

**Supported versions: latest release only.** There are no backports. Upgrading is the only route to a fix.

**No public audit.** The Trust Center at `trust.netbird.io` says the company runs annual third-party penetration tests. The reports sit behind a "Request Access" form. Nothing is downloadable. The footer shows GDPR, ISO 27001, and DORA badges, with the certificates behind the same form. The CISPA relationship is investment and incubation, not audit. `netbird.io/security` returns 404.

Treat the audit posture as a claim, not evidence. Pangolin's posture is worse — no advisories at all — but NetBird's is not verified either.

### 9.5 Breaking changes and upgrade coupling

Recent releases carry real breakage:

- **v0.60.0** — SSH breaking change. The port moved 44338 → 22022. Authentication moved from machine keys to JWT identity. Implicit firewall rules were removed, so an explicit ACL is now required. A specific upgrade order applies.
- **v0.61.0** — "Breaking change for self-hosted deployments". **The management server must be upgraded before the clients.**
- **v0.69.0** — CrowdSec for the reverse proxy adds another container.
- **v0.75.0** — the desktop client was rewritten from Fyne to Wails v3.
- **v0.76.0** — the IPC fix now requires root to enable the SSH server, enable SSH root login, disable SSH auth, or change the management URL.
- **v0.76.1** — PR #6965 "requires an upgrade of both Management and Proxy containers. New proxy under old management **silently disables cost metering**."

The pattern is management-first ordering, container topology changes inside minor versions, and at least one silent version-skew failure. **A self-hoster must read every release note.**

### 9.6 If NetBird GmbH changes the license

- **The grants are irrevocable for released versions.** The client is BSD-3. Management, Signal, Relay, and Combined are AGPLv3. The dashboard is AGPLv3. All of it can be forked.
- **A fork is more realistic than for Pangolin.** The whole stack is Go, one repo, one `go.mod`, plus a React dashboard. There is no Yaegi plugin, no vendor tarball, and no Next.js build ceremony.
- **The relicense precedent exists.** One license change already happened in 2025. A CLA plus VC funding plus a running enterprise/cloud split is the standard setup for further gating.
- **The realistic bad outcome** is that new features land only in the closed `-cloud` images, and Community Edition slowly becomes a demo. Traffic-flow logging is already there — see open issue [#3935](https://github.com/netbirdio/netbird/issues/3935) "Add Traffic Events Logging in Open-Source Version".
- **Data is portable.** SQLite or Postgres, a documented REST API, and a Terraform provider. Exit is real.

## 10. Migration from Tailscale

### 10.1 There is no official migration guide

No page on `docs.netbird.io` covers migration from Tailscale. The only first-party page is a comparison article at `netbird.io/knowledge-hub/tailscale-vs-netbird`.

### 10.2 The CGNAT ranges collide

**Both products use `100.64.0.0/10`.** From [manage-dns](https://docs.netbird.io/how-to/manage-dns-in-your-network):

> "**NetBird IPs**: Management assigns each peer a unique IP from one of 64 possible /16 blocks within the `100.64.0.0/10` CGNAT range (e.g., `100.64.0.0/16` through `100.127.0.0/16`). The block is randomly selected per account and **can be customized**."

Interface names do not collide. NetBird uses `wt0` (`client/iface/configurer/name.go`: `const WgInterfaceDefault = "wt0"`). Tailscale uses `tailscale0`.

**The real hazard is stale Tailscale firewall state.** A NetBird user reported it in the netbirdio repo ([discussion #6834](https://github.com/netbirdio/netbird/discussions/6834)):

> "The problem turned out to be old Tailscale iptables state on the destination machine… `-A ts-input -s 100.64.0.0/10 ! -i tailscale0 -j DROP`. Since NetBird IPs are also in this space, the incoming packet from the other NetBird peer matched `100.64.0.0/10`. It was arriving through `wt0`, not `tailscale0`, so the stale Tailscale rule dropped it."

> "if you're having issues migrating from Tailscale, remove Tailscale **first**, make sure its iptables rules/chains are actually gone afterwards, then try NetBird again."

Related open threads: [#544](https://github.com/netbirdio/netbird/issues/544) "How to avoid IP conflict with tailscale?" and [discussion #6112](https://github.com/netbirdio/netbird/discussions/6112) "On Windows, Netbird's DNS doesn't work when Tailscale is active".

### 10.3 Side-by-side operation

Side by side is possible, but hostile by default. Two conditions make it work:

1. **Move the NetBird IP block off the Tailscale range before the first peer joins.** The block is per account and customizable. Pick a `/16` that Tailscale does not use, or move NetBird to a different space.
2. **Expect DNS conflict on Linux and Windows.** Both clients try to own the resolver. macOS reports fewer problems.

### 10.4 Order of operations

Conditions come first in each step.

1. Sign up for NetBird Cloud, or stand up the self-hosted server. Decide this first — it changes everything after it.
2. **Set the NetBird IP block before the first peer registers.** Avoid the Tailscale range.
3. Create groups and a setup key. Set the key to reusable with auto-assign groups.
4. Add `services.netbird.clients.default` to one host only. Point `login.setupKeyFile` at a sops secret.
5. Run `netbird status -d` on that host. Confirm `Management: Connected` and `Signal: Connected`.
6. Add a second host on the same LAN. Run `netbird status -d` again. **Confirm `Connection type: P2P` and `host/host`.** If it reads `Relayed`, open inbound UDP 49152-65535 for the agent.
7. Write the access policies in Terraform. Test each one before you move a real service.
8. Add the Network for the Unraid NAS. Use a `/32` resource and a routing peer on `mini`.
9. Move Caddy's upstream targets from tailnet names to NetBird names, one vhost at a time.
10. **Remove Tailscale last, and clear its iptables chains.** Then reboot and re-verify every peer.

### 10.5 What breaks first

Ranked by the evidence above:

1. **Stale Tailscale iptables rules** silently drop NetBird traffic on Linux. Discussion #6834.
2. **LAN peers land on the relay** because a host firewall drops unsolicited inbound UDP on a flat network. See § 3.4 and issue #4990.
3. **DNS conflict** while both clients are installed. Linux and Windows are worse than macOS.
4. **`caddy-tailscale` has no supported NetBird equivalent.** `caddy-netbird` is a community plugin, not first-party. Plan to run Caddy as a normal peer instead.
5. **macOS sleep and wake** on `caya` and `framework`. Issue #2454, open with 59 comments.
6. **Stable nixpkgs is too old.** 0.60.2 predates two high-severity advisories.
7. **Self-hosted upgrade ordering.** Management first, always.

## 11. Summary judgment

**Choose NetBird if** you want a peer mesh with kernel WireGuard on Linux, post-quantum rekeying, device posture checks and SSO at no cost, and an optional public reverse proxy in one product.

**Do not choose NetBird if** you value a single reviewable ACL file, a stable 1.x API, or the lowest possible operational burden. Tailscale is better on all three.

**On the five stated goals:**

| Goal | Verdict |
|---|---|
| 1. Same or more function | **More.** Mesh parity, plus kernel WireGuard, Rosenpass, free posture checks, browser SSH/RDP, and a public reverse proxy |
| 2. Declarative config | **A draw, with a different shape.** Client side is fully declarative in Nix. Control plane is an official Terraform provider with 24 resources, not one HuJSON file |
| 3. Simplicity | **Worse on self-hosted, equal on cloud.** Self-hosting adds a public VM, an upgrade ritual, and a single point of failure |
| 4. Public access with zero trust | **Better.** NetBird Reverse Proxy is a real Funnel equivalent, self-hostable, with SSO, PIN, password, header auth, and geo/IP restriction. It is in beta and needs Traefik |
| 5. Streaming speed | **Better or equal.** Kernel WireGuard on Linux, and confirmed direct host-to-host on the LAN. Watch the firewall trap |

**The honest recommendation.** The speed and LAN questions both come back clean. The declarative question is a real but survivable regression: one HuJSON file becomes one Terraform module. The largest risk is not a feature gap. It is the 0.x version number, the 45 percent open-issue ratio, the 3.5-year IPC hole, and the pace of breaking changes in a daemon that runs as root on five machines.

**If you proceed:**

1. Use `netbird` from **nixpkgs unstable**, never stable 25.11. Stable ships 0.60.2, inside the range of two high-severity advisories.
2. Start with **NetBird Cloud on the free tier**. Five users and 100 machines cover this fleet. Defer the self-hosted control plane.
3. Use `services.netbird.clients.<name>` with `hardened = true` and `login.setupKeyFile` from sops-nix.
4. Set `services.netbird.useRoutingFeatures = "server"` on `mini` and `"client"` elsewhere.
5. **Set the NetBird IP block off `100.64.0.0/10` before the first peer joins**, so it can run beside Tailscale.
6. **Verify `netbird status -d` shows `Connection type: P2P` and `host/host` for LAN pairs.** Open inbound UDP 49152-65535 if it does not.
7. Keep Caddy for the 16 `*.jadee.fyi` vhosts. Run it as a NetBird peer. Treat NetBird Reverse Proxy as a later experiment while it is in beta.
8. Manage groups, policies, networks, and DNS with the official Terraform provider. Commit the config to this repo.
9. Read every release note. Upgrade Management before the clients.
10. If you later self-host: the nixpkgs `services.netbird.server` module tracks the pre-0.62 architecture. It needs an external IdP and Coturn. Package `combined/` yourself, or run the container.
